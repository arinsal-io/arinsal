# arinsal-ets

This crate provides VM-independent ETS storage and match specifications over `arinsal-term`. The VM must enforce table protection, process ownership, and owner lifecycle.

`Registry` holds named and unnamed tables. General stored objects own exact-size allocations; lookups copy into a caller heap. `ConcurrentTable` divides keys across caller-selected, cache-line-padded shards; the mixed example defaults to 2,048 shards. A set containing two small integers keeps the pair directly in an atomic shard slot when space is available. Writers lock that shard, while readers use a version check and build the result tuple on the caller heap without locking or copying a stored term. Other shapes and full shards use the general copy path. Multi-object inserts lock every shard and publish through a table-wide version check.

Hash traversal follows OTP 29.1.1's dynamic linear hash slot calculation, key grouping, and bucket order. `first`, `next`, `last`, `prev`, `slot`, `tab2list`, and `select` expose their distinct OTP ordering. `slot` returns an ETS object list for every table type. `safe_fixtable` keeps deleted keys available to `next` until the final unfix and suppresses bucket growth while fixed. Hash tables join up to five buckets after a large-table delete when the OTP shrink threshold is reached. The differential tests compare exact order; they do not normalize results.

Ordered tables use a counted treap, giving `slot` O(log n) and key-range selection O(log n + returned matches). `ConcurrentTable` uses independently locked ordered trees for writes. Numeric keys are routed by their loose numeric value, and complex keys share one stripe so equal keys cannot split across stripes. This is a striped scheme rather than a CA tree; cross-stripe ordered traversal is not exposed by `ConcurrentTable`.

`match_spec::MatchProgram` is independent of ETS and reusable by tracing. It validates bound variables and the OTP 29 guard BIF table, evaluates list expressions, and returns `'EXIT'` for a failing body expression as OTP does. `compile_trace` accepts tracing forms and dispatches their effects through `MatchContext`; the tracing subsystem must supply that context. Context-aware table selection passes process-dependent values to the interpreter. `SelectContinuation` encodes ordered 8-tuples and hash 6-tuples, with an opaque program reference retained by the compiled `MatchProgram`. The caller must keep that program and table identity available when decoding a continuation. Hash chunk splitting follows OTP's distinct first-call and continuation list handling.

`info_item` and `info_list` expose the ETS property keys. `safe_fixtable_for_at` accepts the VM's exact fixation timestamps and tracks per-process counts for `safe_fixed` and `safe_fixed_monotonic_time`; `safe_fixtable` generates local timestamps when called directly. `memory_words` counts Rust table and object allocations in machine words; it differs from erts because its table headers, bucket arrays, locks, and allocator accounting differ. `BigCounterOp` accepts arbitrary precision increments and thresholds. `CountContinuation` encodes the internal five-element `select_count` trap state. `match_spec_test` handles valid specifications; the compiler's complete diagnostic strings for invalid specifications are not implemented.

The differential tests use `RefErl` and compare exact lookup, slot, traversal, and table-list ordering. The `mixed`, `micro`, and `offset` examples are performance probes, not assertions about production latency.
